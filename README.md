# Bellwake

Bellwake — система доставки обязательных уведомлений на рабочие станции. Администратор создаёт уведомление в веб-интерфейсе, сервер публикует его в MQTT в заданное время, а настольный агент показывает окно поверх остальных приложений и при необходимости требует подтверждение прочтения.

Проект состоит из трёх частей:

- `admin/` — веб-интерфейс администратора на Vue 3 и Bootstrap 5;
- `backend/` — API, Socket.IO, планирование уведомлений, MQTT и работа с MySQL;
- `src/` и `src-tauri/` — настольный агент Tauri для macOS и Windows.

## Как устроена доставка

1. Администратор создаёт или изменяет уведомление через Bellwake Admin.
2. Сервер хранит даты в UTC и регулярно сверяет активные уведомления с MySQL.
3. Когда наступает `starts_at`, сервер публикует retained-сообщение в `bellwake/notifications/<notification_id>`.
4. Агент получает идентификатор, загружает содержимое через API и показывает окно.
5. Для обязательного уведомления подтверждение записывается в `notification_ack`. Повторно этому сочетанию устройства и пользователя уведомление не показывается.
6. После `expires_at`, перевода в неактивное состояние или удаления сервер снимает retained-сообщение.

MQTT не содержит текст уведомления — только его идентификатор. Содержимое и право показа агент получает от API организации.

## Конфигурация организаций

Единственный источник настроек конкретной организации — `backend/.env`. Этот файл создаётся из `backend/.env.example`, не входит в Git и не должен попадать в сборки или публикации. Сам `backend/.env.example` намеренно отслеживается Git, входит в публикацию на GitHub и служит обязательным шаблоном конфигурации для новых установок.

В исходном коде не зафиксирован домен организации. `BELLWAKE_DOMAIN`, параметры MySQL, MQTT и развёртывания читаются из `.env`. Веб-интерфейс обращается к `/api` на своём домене, а агент получает адрес сервера организации при первоначальной регистрации.

Исключение — единый официальный Cloudflare Relay:

`bellwake-relay.ovsyannikov-ivan.workers.dev`

Его адрес намеренно встроен в сервер и агент. Relay используется только для первоначальной привязки, обслуживает все организации и не хранит их конфигурацию. `RELAY_SEND_TOKEN` в `.env.example` также общий для официального Relay: его не нужно генерировать или менять при обычной установке. Замена токена требует собственного Cloudflare Worker, синхронной замены его секрета и пересборки клиента с новым адресом Relay.

## Требования

Для сервера:

- Debian или Ubuntu;
- Node.js и npm;
- MySQL 8 с заранее созданными пустой базой и пользователем;
- TLS-сертификат домена, по умолчанию от Let's Encrypt;
- права `sudo` для установки и настройки Mosquitto;
- PM2 для постоянного запуска backend.

Для сборки агента дополнительно нужны Rust и системные зависимости Tauri 2. Сборка Windows выполняется на Windows, сборка macOS — на macOS.

## Первоначальная настройка сервера

Установите зависимости backend:

```bash
cd backend
npm ci
```

Запустите общую настройку:

```bash
npm run setup
```

Команда последовательно выполняет:

- `npm run setup:env` — создаёт или дополняет `.env`, запрашивает домен и параметры MySQL, генерирует секрет организации;
- `npm run setup:broker` — устанавливает и настраивает Mosquitto, TLS, пользователей и ACL;
- `npm run setup:db` — создаёт отсутствующие таблицы, применяет идемпотентные миграции и при пустой таблице `users` интерактивно создаёт первого администратора.

Для первого администратора установщик запрашивает логин, отображаемое имя и пароль длиной не менее 12 символов. Пароль хешируется Argon2id с индивидуальной солью и не записывается в `.env`, журналы или Git. Публичной регистрации и пароля по умолчанию нет.

`setup:db` не создаёт саму базу или пользователя MySQL, не удаляет и не пересоздаёт рабочие таблицы, не очищает существующие данные. Повторный запуск сохраняет существующих пользователей и их пароли. Если таблицы уже мигрированы, сценарий только проверит структуру и сообщит, что администратор существует.

Создать первого администратора отдельно после применения схемы можно командой:

```bash
npm run setup:admin
```

Сценарий настройки брокера ожидает TLS-файлы:

```text
/etc/letsencrypt/live/<BELLWAKE_DOMAIN>/fullchain.pem
/etc/letsencrypt/live/<BELLWAKE_DOMAIN>/privkey.pem
```

При других путях добавьте `MQTT_CERT_FILE` и `MQTT_KEY_FILE` в `backend/.env` до запуска `setup:broker`.

## Запуск backend

Для разработки:

```bash
cd backend
npm run dev
```

Для постоянного запуска через PM2:

```bash
cd backend
pm2 start ecosystem.config.cjs
pm2 save
```

Проверка состояния доступна по `GET /api/health`.

### Публикация backend

В `backend/.env` можно задать:

```dotenv
DEPLOY_SSH_TARGET=user@example.org
DEPLOY_SSH_PORT=22
DEPLOY_REMOTE_DIR=/var/www/example.org/backend
DEPLOY_PM2_APP=bellwake-api
```

После этого:

```bash
cd backend
./deploy.sh
```

Сценарий копирует исходники без `.env` и `node_modules`, выполняет на сервере `npm ci --omit=dev` и перезапускает указанное приложение PM2. Серверный `.env` сохраняется.

При обновлении со схемой БД сначала создайте резервную копию, затем опубликуйте файлы без немедленного перезапуска:

```bash
DEPLOY_SKIP_RESTART=true ./deploy.sh
```

После `npm run setup:db` на сервере перезапустите процесс PM2 вручную. Это не позволяет новому backend стартовать раньше обязательной миграции.

## Bellwake Admin

Для разработки сначала запустите backend, затем:

```bash
cd admin
npm ci
npm run dev
```

Интерфейс откроется на `http://127.0.0.1:5173`; Vite проксирует `/api` и WebSocket на `http://127.0.0.1:3102`.

При открытии интерфейс сначала проверяет серверную сессию через `GET /api/auth/me`. Без действующей сессии показывается форма входа. После успешного входа подключается защищённое пространство Socket.IO `/admin`. Выход отзывает серверную сессию, отключает Socket.IO и возвращает форму авторизации.

Административные сессии:

- имеют криптографически случайный идентификатор, в MySQL хранится только его SHA-256;
- передаются через cookie `HttpOnly`, `Secure`, `SameSite=Strict` и не попадают в `localStorage`;
- сохраняются в таблице `sessions`, поэтому переживают перезапуск Node.js;
- имеют ограниченный срок действия, поддерживают logout и ручной отзыв;
- проверяются при подключении Socket.IO, перед каждым административным событием и периодически во время соединения;
- используют отдельный CSRF-токен для изменяющих REST-запросов и подключения Socket.IO.

После пяти неверных паролей для пары логин/IP вход временно ограничивается. Отключённые пользователи с `is_active = 0` не могут создавать новые сессии, а их действующие сессии перестают проходить серверную проверку.

Сборка:

```bash
cd admin
npm run build
```

Содержимое `admin/dist/` публикуется в корень сайта организации. В рабочей среде обратный прокси должен направлять `/api` на backend и поддерживать переключение протокола WebSocket для `/api/socket.io`.

API авторизации:

- `POST /api/auth/login` — проверяет пароль и создаёт серверную сессию;
- `GET /api/auth/me` — возвращает текущего администратора и обновлённый CSRF-токен;
- `POST /api/auth/logout` — отзывает сессию и немедленно отключает связанные административные сокеты.

Список и содержимое уведомлений, операции создания, изменения и удаления, а также подтверждение QR-подключения доступны только действующей административной сессии. Агентские маршруты `/api/enroll`, `/api/notifications/:id/delivery` и `/api/notifications/:id/acknowledge` продолжают использовать отдельный `clientToken`.

## Настольный агент

Установка зависимостей:

```bash
npm ci
```

Запуск для разработки:

```bash
npm run tauri -- dev
```

Кроссплатформенная обёртка запускает Tauri и в macOS, и в Windows. На macOS она повторно использует сохранённые в Keychain учётные данные, чтобы отладочная пересборка не запрашивала доступ при каждом запуске.

Сборка установочного пакета:

```bash
npm run tauri -- build
```

Артефакты появляются в `src-tauri/target/release/bundle/`. На macOS создаются `.app` и `.dmg`; на Windows — установщики, поддерживаемые Tauri.

Новый агент связывается с организацией через QR-код и единый официальный Relay. После регистрации адрес API и несекретные параметры MQTT сохраняются в `settings.json`, а `clientToken` и пароль MQTT — в системном хранилище учётных данных. `enrollmentToken` на клиенте не сохраняется.

Bellwake работает как фоновый пользовательский агент. В macOS он не занимает место в Dock и показывает штатную иконку в Menu Bar; в Windows не занимает место на панели задач и показывает иконку в System Tray. Окно открывается только для первоначальной настройки или полученного уведомления, а после подтверждения снова скрывается. Rust-процесс и MQTT-соединение при этом продолжают работать. Иконка Menu Bar в macOS является монохромным template image и автоматически меняет цвет вместе со строкой меню; в Windows System Tray использует цветной логотип Bellwake.

## База данных и время

Bellwake использует таблицы:

- `users` — администраторы Bellwake Admin и их хеши паролей Argon2id;
- `sessions` — ограниченные по времени серверные сессии администраторов;
- `login_attempts` — краткоживущий журнал для ограничения неверных попыток входа;
- `pairing_requests` — одноразовые подтверждения QR-подключений;
- `notifications` — уведомления и период действия;
- `devices` — зарегистрированные устройства;
- `device_users` — пользователи устройств, токены повторной регистрации и ссылка `enrolled_by_user_id` на администратора;
- `notification_ack` — подтверждения обязательных уведомлений.

`users` и `device_users` описывают разные сущности: первая таблица содержит администраторов веб-интерфейса, вторая — пользователей macOS/Windows с агентом Bellwake.

### Учёт администратора при QR-подключении

1. Авторизованный администратор подтверждает UUID v4, отсканированный из окна агента.
2. Backend создаёт запись `pairing_requests`, связывает её с `users.user_id`, генерирует криптографически случайный одноразовый токен и хранит только его SHA-256.
3. Токен передаётся агенту через официальный Relay в уже существующем поле `enrollmentToken`. Формат QR-кода и протокол Relay не изменяются.
4. Агент вызывает обычный `/api/enroll`. Backend атомарно проверяет срок и однократность токена, регистрирует устройство, помечает запрос использованным и только после этого записывает `device_users.enrolled_by_user_id`.
5. Обычное обновление по `clientToken` не меняет `enrolled_by_user_id`. Ручной enrollment с общим токеном организации оставляет поле `NULL`, а новое явное QR-подключение существующего агента обновляет ссылку на последнего администратора.

Успешная передача пакета через Relay означает только доставку одноразового токена. Связь с администратором считается завершённой исключительно после успешной транзакции enrollment.

### Обновление существующей базы

Перед обновлением создайте резервную копию MySQL и убедитесь, что можете восстановить её. После публикации backend выполните в его непубличном каталоге:

```bash
npm ci --omit=dev
npm run setup:db
```

Сценарий создаёт новые таблицы и через проверку `information_schema` безопасно добавляет `device_users.enrolled_by_user_id`, индекс и внешний ключ. Он работает и на пустой, и на действующей базе, не выполняет `DROP TABLE`, не очищает уведомления, устройства или подтверждения и допускает повторный запуск.

Безопасный порядок публикации новой версии:

1. сделать резервную копию базы данных;
2. опубликовать backend без перезаписи серверного `.env`;
3. установить production-зависимости и выполнить `npm run setup:db`;
4. проверить вход первоначального администратора и `GET /api/health`;
5. собрать и опубликовать `admin/dist/` в web root;
6. перезапустить backend через PM2 и проверить авторизацию, Socket.IO и QR-enrollment.

API передаёт даты в UTC ISO 8601. Backend преобразует их в MySQL `DATETIME` UTC через Luxon. Веб-интерфейс показывает локальное время браузера и также использует Luxon для преобразования в UTC и обратно.

## Безопасность репозитория

- Не добавляйте `backend/.env`, закрытые ключи TLS, дампы базы и локальные настройки в Git.
- Не удаляйте `backend/.env.example` из Git: он должен публиковаться на GitHub как шаблон конфигурации.
- `ENROLLMENT_TOKEN`, пароли MySQL и MQTT уникальны для организации и создаются или вводятся при настройке.
- Общий `RELAY_SEND_TOKEN` в `.env.example` относится только к единому официальному Relay и не заменяет секреты организации.
- Перед публикацией проверяйте `git status` и содержимое подготовленного commit.
